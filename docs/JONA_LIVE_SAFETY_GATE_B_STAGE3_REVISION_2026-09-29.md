## 1. Revised IMMEDIATE_DANGER intervention architecture

### The four options, evaluated

| | **A. Hard termination**<br>`Live → close → static message` | **B. Restricted Live replacement**<br>`Live → close → mint restricted Live → continue` | **C. Restricted non-Live safety pathway**<br>`Live → close → server-controlled text turn, spoken via browser TTS` | **D. Other** |
|---|---|---|---|---|
| **Child safety (content)** | Safe by omission — no further content at all | Weaker: Live's per-turn output is still freely generated by Gemini under a locked *system instruction*, but nothing constrains the actual reply text turn-by-turn the way a structured server call can | Strongest: every restricted reply is a normal server-side `generateContent` call the same policy layer already governs (the same `RESTRICTED_SAFETY_SYSTEM` swap Ask Jona already uses), so HSD reviews/controls content per turn, not just at connection-mint time | Considered; see below |
| **Engagement (keep child present long enough to encourage help)** | Worst — Jona vanishes at the exact moment of disclosure, which is the opposite of the stated goal | Good — natural realtime voice continues | Good, with one real cost: turn-based (speak → transcribe → reply → speak) rather than full-duplex, so it feels a beat slower than Live, but still voice-in/voice-out and still present | — |
| **Latency** | Fastest to silence (single close) | Adds a full Live reconnect (new ephemeral token mint + new WebSocket handshake) before Jona can speak again | Adds one `generateContent` round-trip (short prompt, short output) — slower than Live's streaming duplex, faster than a second full Live handshake | — |
| **Server control** | N/A — nothing further is generated | Locked only at connection-mint time; per-turn content is still Gemini Live's own realtime generation | Full — server sees and can constrain the exact reply text before any audio is produced | — |
| **Tampered-client risk** | Same ceiling as always: a modified client can ignore the directive and keep the original connection open (Stage 3 §4.5) | Same ceiling, plus a second point of trust: the client must also honestly request the *restricted* token and not a default one (mitigated in §4 below) | Same base ceiling (client can ignore the close directive on the original connection), but the *replacement* pathway is not itself a second Live trust surface — it's the same request/response shape Ask Jona already uses under HSD's server | — |
| **Quota / cost abuse** | Cheapest — no further generation | Most expensive — a second Live session (ephemeral token + streaming minutes) just for a narrow, short exchange | Cheapest of the "keep Jona present" options — a handful of short `generateContent` calls, same pricing tier Ask Jona already uses | — |
| **Privacy** | Best — no further audio to any vendor | Worst of the three "keep Jona present" options — raw child audio keeps streaming to Gemini Live during the highest-risk window | Better — raw audio never reaches Gemini during the danger window; speech-to-text runs through the browser's own local/OS speech recognition (the same class of browser-native capability `browserNarration.js` already uses for output), and only transcribed text goes to HSD's server | — |
| **Failure modes** | Simplest — one thing to fail (the close call itself) | Two things must succeed in sequence under crisis conditions: token mint, then reconnect — a failure here has no natural next fallback other than dropping to A anyway | One thing to fail (the `generateContent` call) with a clean, natural fallback to A if it does | — |

**D (other) was considered and rejected as a fourth branch:** a hybrid where the *first* restricted turn is Live (for the least possible latency at the exact moment of disclosure) and every turn after that switches to C's text pathway. This was rejected for this design because it reintroduces B's core weakness — one turn of unconstrained Live generation — for a latency saving that §3 below shows is not actually the bottleneck (the classification/Firestore round-trip dominates total detection latency far more than "Live vs. one `generateContent` call" does). Not worth the added complexity and the added trust surface.

### Recommendation: **C — restricted non-Live safety pathway**

This is not a new architecture so much as **reusing Ask Jona's already-built, already-trusted restricted-safety mechanism** (`RESTRICTED_SAFETY_SYSTEM` prompt-swap in `chat.js`) as the Live product's fallback lane, narrated aloud instead of read on-screen. It directly matches your stated purpose — *acknowledge → orient toward immediate safety → encourage trusted-human help → remain calm and brief* — because that restricted system prompt is already written to be narrow and non-therapeutic; it does not need a new, less-proven "restricted Live persona" invented and locked into a brand-new token type.

**Sequence, precisely:**

1. `live-transcript-classify.js` classifies `IMMEDIATE_DANGER`, writes `safetyTier` + `interventionDirective: { action: "restricted_safety_pathway" }` to Firestore (replaces the old `end_session_immediate_danger` action name from Stage 3 §4 — the session does not fully end here, it transitions).
2. Browser's `onSnapshot` fires. In order:
   a. Mute/pause the currently-playing Live audio immediately (client-side, synchronous — unchanged from Stage 3 §4.3.a).
   b. `session.close()` on the Gemini Live WebSocket — the *generative, full-duplex* connection ends here and does not reopen. (Unchanged from Stage 3 — this part of "Jona's normal Live voice stops" stands exactly as designed.)
   c. The browser starts listening via its own local speech-recognition capability (new, small client utility — see §5) instead of reopening a Gemini Live socket.
   d. Each utterance the child speaks while in this state is transcribed locally, sent to the server as plain text, run through `_safetyEngine.js`/`_safetyPolicy.js` exactly as any other turn (so a continued escalation, e.g. stating a specific immediate plan, is still tracked — this pathway does not turn off classification, it only changes the delivery mechanism), and answered by a single `generateContent` call using the same `RESTRICTED_SAFETY_SYSTEM` swap Ask Jona uses, scoped additionally to the four allowed moves above and nothing else (no open Q&A, no lesson content, no therapy).
   e. The reply text is read aloud via `browserNarration.js` (already in this codebase, already used elsewhere, does not touch Gemini Live at all).
3. **Bounded duration, not indefinite:** this pathway is capped — a small fixed number of exchanges (recommend 3–4) or a short wall-clock cap (recommend 2–3 minutes), whichever comes first, matching "narrow," not open-ended. At the cap, it ends with the same static bilingual message Stage 3 §4 already specified (*"Jona needs to stop for now..."*), read aloud, then a full session end — this is where Option A's static-message ending is still used, just moved to be the pathway's natural close rather than its opening move.
4. **Any failure inside this pathway (the `generateContent` call errors, the browser's speech recognition is unavailable/denied, the cap is reached) falls back immediately to Option A** — mute (already done), static message, session end. The child is never left in a silent, broken state; the fallback floor from Stage 3 §4 is preserved exactly, just demoted from "the whole design" to "the safety net under the improved design."
5. Server-side, independently of the browser (unchanged from Stage 3 §4.4–4.5): `live-session-end.js` records the eventual end with reason `immediate_danger_intervention`, the concurrency lock is released, and a future-token cooldown/review window is set for the account regardless of what the client does or doesn't honestly execute.

**What does not change from Stage 3:** the tampered-client ceiling (§4.5's honest statement that a modified browser can ignore the close directive and keep the original Live socket open); the standing, always-on system-instruction floor recommendation (§4.6); harm-to-others `IMMEDIATE_DANGER` (matrix row 12) follows the identical sequence — this design does not distinguish self-harm from harm-to-others for the intervention mechanism, only the wording of the spoken guidance differs, which is a content decision for `_safetyPolicy.js`/the restricted prompt, not an architecture decision.

**Explicitly still true:** no automatic emergency-service contact, no automatic parent/guardian notification anywhere in this pathway — consistent with your standing instruction.

## 2. NORMAL pre-filter — removed for child beta

**Decision: remove early-exit-to-NORMAL from `_safetyEngine.js` for the child beta.** Every substantive transcript chunk goes to the full contextual classifier.

**The one thing that survives, and why it isn't the same risk:** an exact-empty or whitespace-only transcript chunk (a transcription event with literally zero characters — silence, a dropped audio frame, a transcription artifact with no text) is never sent to the classifier, because there is no text to classify, not because a judgment call decided it was safe. This is a null-input guard, not a semantic pre-filter, and it has no false-negative surface — there is nothing in an empty string that could have been a disclosure. Every string with actual content, including "ok," "thanks," or a single word, goes through the full classifier.

**Comparison, as requested:**

| | Pre-filter → classifier only when "potentially relevant" | Every substantive transcript → classifier |
|---|---|---|
| **Latency saved** | None that matters — classification is already asynchronous and off the response-blocking path (Stage 3 §4, unchanged: Jona's spoken reply never waits on this call either way). The only thing a pre-filter saves is *supervisor* latency on trivial turns, which has no user-facing effect since nothing is blocking on it. |
| **Cost saved** | A `_safetyEngine.js` call is a short-context, short-output structured `generateContent` call — Gemini Flash-tier pricing, sub-cent per call. Skipping it for an estimated 10–20% of turns that are trivial acknowledgments ("ok," "thanks," "yeah") saves a small fraction of an already-small per-session cost — realistically fractions of a cent per session. |
| **Safety cost of a false negative** | The entire point of a false-negative-in-the-optimization-layer failure mode: a pre-filter that wrongly clears a real disclosure means the contextual classifier — the only thing in this design that actually understands register/intent/imminence — never runs on that turn at all. There is no downstream recovery for a turn the classifier never sees. |
| **Verdict** | The cost side is negligible (fractions of a cent, zero user-facing latency change); the risk side is a full missed classification on a real disclosure. Not a defensible trade for a child safety beta. |

This directly implements your instruction: *"Do not optimize away safety classification unless the early-NORMAL mechanism has an extremely narrow, demonstrably safe scope."* The only surviving exception (empty string) meets that bar because it has no semantic content to misjudge; nothing else does.

## 3. Measurable safety latency targets

**Standing framing, stated explicitly per your instruction:** there is **zero intentional blocking latency on the normal conversational path** — Jona's spoken reply to any turn never waits on the classifier, the policy engine, or Firestore, in any tier, including this revision's changes. Separately, and not in tension with that, there is **non-zero detection/intervention latency** — the time between a risk-bearing utterance and the system actually reacting to it. Both must be measured; neither claim substitutes for the other.

### Instrumented timestamps (per turn, logged as durations only — no transcript content, consistent with metadata-only logging)

| Point | Event |
|---|---|
| T0 | Learner speech-end (Gemini Live's own end-of-utterance/turn-detection signal) |
| T1 | Transcript chunk available to the browser (`inputAudioTranscription` arrives on the WS) |
| T2 | Classifier request dispatched (`live-transcript-classify.js` invoked with that chunk) |
| T3 | Classifier verdict received (tier + directive written to Firestore) |
| T4 | Intervention directive received by the client (`onSnapshot` fires) |
| T5 | Client stops the currently-playing audio (mute executes) |
| T6 | Restricted response begins (first word of the restricted-pathway reply, or the static message, actually starts playing) |

### Derived intervals and thresholds

| Interval | Definition | Target | Warning | Unacceptable |
|---|---|---|---|---|
| Transcript availability | T1 − T0 | < 1s | 1–3s | > 3s |
| Classifier dispatch | T2 − T1 | < 200ms | 200ms–1s | > 1s |
| Classifier compute | T3 − T2 | < 1.5s | 1.5–3s | > 3s |
| Firestore propagation | T4 − T3 | < 500ms | 500ms–2s | > 2s |
| Client mute execution | T5 − T4 | < 100ms | 100–500ms | > 500ms |
| **Total: disclosure → audio muted** | T5 − T0 | **< 3s** | **3–6s** | **> 6s** |
| **Total: disclosure → restricted response begins** | T6 − T0 | **< 5s** | **5–9s** | **> 9s** |

An "unacceptable" reading on any row is a Stage 4 blocker for that specific stage of the pipeline, not a reason to relax the target — the fix is to find and address the slow stage (e.g., a slow classifier prompt, a Firestore region mismatch), not to widen the threshold.

### What Stage 4 must actually do with this

- Log all seven timestamps, keyed by `sessionId` + a per-turn identifier, to the existing metadata-only audit trail (extends `live-session-end.js`'s existing fields — durations and tier only, matching the "no trigger-snippet retention" rule already in place).
- Surface the six derived intervals (min/median/p95) in the admin dashboard already planned for Stage 2/3 visibility work, so real numbers from admin testing replace every estimate in this section before any child-facing release decision.
- The mute-execution row (T5 − T4) is the one figure that should be trivially fast and stay fast; a regression there is a client bug, not a network/model variance, and should be treated as a correctness defect, not a latency tuning problem.

## 4. Restricted-session state inheritance

**Principle:** the HSD-level `sessionId` (the Firestore session document), not the underlying Gemini connection, is the unit of continuity. Safety state is keyed to `sessionId`, and any *server-initiated* reconnect or pathway-switch that happens as part of the safety system's own reaction (§4's `HIGH_RISK` Live remint, or this revision's `IMMEDIATE_DANGER` restricted-pathway switch) must carry the same `sessionId` and therefore the same sticky state forward automatically, by construction — it is never a fresh session in the sense §3 of the base Stage 3 document means when it says "the next session starts at `NORMAL`."

**What changes to enforce this, precisely — the gap this closes:** Stage 3 already stated the `sessionId` persists across `HIGH_RISK`'s reconnect (§4), but did not specify what stops a client from independently requesting an ordinary token for that same account while the server holds an elevated state. This revision adds an explicit server-side rule:

- **`live-token.js` becomes the authority, not the client's requested flag.** Before minting any token (default or restricted), it looks up the current `safetyTier` for the caller's active/most-recent `sessionId`. A client-supplied `restricted: true/false` value is advisory only — the server decides the actual system-instruction variant to mint based on its own held state, never purely on what the client asked for.
- If the looked-up state is `HIGH_RISK`, only the restricted-support Live token variant may be minted for that `sessionId`, regardless of what the client requests.
- If the looked-up state is `IMMEDIATE_DANGER`, **no Live token is minted at all** — per §1's revised architecture, that state's continuation (if any, within its bounded exchange cap) uses the non-Live restricted pathway, not a Live reconnect. A request for a Live token against a `sessionId` in this state is refused outright.
- This check is the same mechanism already needed for the ordinary `HIGH_RISK` reconnect (Stage 3 §4 already implies the server must know to mint restricted, not default) — this revision just makes explicit that the check is authoritative and keyed to server-held state, so a reconnect can never silently degrade back to an ordinary session because of a client-side bug or a tampered request.
- **A genuinely new session (the child closes Talk with Jona and opens it again later, or reconnects with no continuity to a prior `sessionId`) is unaffected and correctly starts at `NORMAL`** — this is the already-approved, intentional "no permanent profile label" behavior and is not being changed. The fix above only closes the gap where a reconnect that is *part of the safety system's own handling of an in-progress session* could be mistaken for a new one.

## 5. Resulting changes to the Stage 4 file plan

Relative to Stage 3's implied file list and Stage 2 Rev2's file list (`_safetyEngine.js`, `live-transcript-classify.js`, `live-token.js`, `live-session-end.js`, `TalkWithJona.jsx`, `firestore.rules`, `AdminLiveJonaTab.jsx`):

**New:**
- A small client-side speech-input utility for the restricted, non-Live pathway (browser-native speech recognition, not routed through Gemini) — parallels `browserNarration.js`'s existing role for output.
- A thin restricted-pathway turn handler reusing `chat.js`'s existing `RESTRICTED_SAFETY_SYSTEM` construction, scoped to the four allowed moves from §1, with the exchange-count/wall-clock cap from §1.3.

**Modified, beyond what Stage 3 already specified:**
- `_safetyEngine.js` — remove the early-NORMAL pre-filter entirely except the exact-empty-string guard (§2). This is a *simplification* of the Stage 3 design, not an addition.
- `live-token.js` — add the authoritative server-side safety-state lookup before minting any token, superseding a client-supplied `restricted` flag (§4). This is additive to, not a replacement of, Stage 3's existing lock-`inputAudioTranscription`/`outputAudioTranscription` work.
- `live-transcript-classify.js` / session doc schema — change the `IMMEDIATE_DANGER` `interventionDirective` action from `end_session_immediate_danger` to `restricted_safety_pathway` (§1), and add the bounded-exchange counter and wall-clock cap as session-doc fields.
- `live-session-end.js` / session doc — add the seven-timestamp instrumentation fields from §3 (durations only, no content), and add `immediate_danger_intervention` as an end reason reachable either from the restricted pathway's natural cap or from any fallback-to-Option-A failure inside it.
- `AdminLiveJonaTab.jsx` — surface the §3 latency percentiles, not just the existing safety-tier visibility Stage 2/3 already specified.

**Explicitly not changed by this revision:** the `HIGH_RISK` hard-reconnect mechanic (still Live, still a locked restricted system instruction, per Stage 3 §4 as written), the decision matrix, the state machine's monotonic/sticky rules, the supervisor failure-policy thresholds, and everything scoped out of Gate B entirely (Ask Jona's `chat.js` migration, parent/school notification, automatic emergency-service contact).
