## Working conventions confirmed this session (carry forward)

- **Production deploys need fresh, explicit, unambiguous authorization each time** — a bare "deploy" is not enough; disambiguate (draft vs. production) before acting, and even after disambiguating, favor an extra explicit confirmation before executing something as consequential as a production push. This was directly tested this session: the user challenged an earlier production deploy over exactly this ambiguity, and the reconciliation that followed set the standard for the rest of the session.
- **Before any production push:** check whether prod has drifted since the reviewed commit's base, confirm the exact deployed SHA via independent evidence (not just a deploy title string — manual `netlify deploy` does not set `commit_ref`; use content-level evidence like matching bundle hashes or, for functions, the deployed function manifest via `netlify-cli functions:list`), and re-verify tests/build immediately before deploying, not just at review time.
- **Never claim a security/child-safety property without reading the current code.** Several real findings this session only surfaced by tracing actual call paths (e.g., `useAuth.jsx`'s `activeProfileId` default) rather than trusting an existing comment or a prior commit's test results — "do not treat historical test results as current verification" was explicit user guidance and proved correct in practice (the profileId-normalization gap was real).
- **Never claim a live production behavior was verified without a real authenticated session** — mocked/unit tests are not a substitute for live confirmation, and this distinction was required to be stated plainly rather than blurred, every time.
- **Deploy convention:** `npx netlify-cli deploy --prod --dir=dist --site=7e00bee1-f9c5-4afb-a43d-a786cb86cb77` (add `--skip-functions-cache` for backend/functions changes specifically, to force a fresh bundle rather than risk a stale cached one).
